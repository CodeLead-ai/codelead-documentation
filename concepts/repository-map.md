# The repository map

The repository map is CodeLead's summary of a repository: the stack, the validation commands, the modules and the entry points. CodeLead writes it from the code, with no model call, into two files in `docs/codelead/`. Other parts of CodeLead read it, so that each request starts from the same picture of the code.

**In short**
- The map is `docs/codelead/repository-map.md` for people and `repository-map.json` for programs.
- [`codelead init`](../cli/codelead-init.md) writes the first map. [`codelead map`](../cli/codelead-map.md) and [`/map`](../chat-commands/map.md) read the repository again when the map is stale.
- A stamp tells whether the map is fresh: the same git head, and a file count within 2%.
- Each map that is written adds its facts to the [encyclopedia](knowledge-base.md) (CodeLead's list of facts about the repository) and writes one [evidence record](evidence-records.md).

## Why it exists

Without a map, no person can see what CodeLead believes about the code. The map makes that belief a file. You read it, you commit it, and you see it change when the code changes. The [preflight](requests-plans-and-patches.md) and the chat start from it, so that a model gets the same summary each time.

## How it works

CodeLead builds the map from the [project library](project-library.md), the index of the files, the modules, the symbols and the relationships. The map keeps the summary and the relationships. For an old application whose stack CodeLead knows, the map also says what the [System Model](../modernization/system-model.md) has read. The System Model is CodeLead's description of an old application, read from its sources.

A real map read on the Basic Store sample, when the kept map is fresh:

```console
codelead map
```

```output
Repository map is fresh: 1 module, 89 files; docs/codelead/repository-map.md
Entry points: WebApplication1/webapp.csproj
Stamp: git bd30c0ac3c5f (uncommitted changes), 89 files scanned, written 2026-11-20T04:57:58.426Z
```

The start of `docs/codelead/repository-map.md`, as `codelead map` wrote it:

```output
# Repository map

<!-- Generated by CodeLead (codelead map) from the code, with no model call. Rewritten by codelead map --refresh; not edited by hand. -->

**Stack:** C#, JavaScript; tools: .NET; an existing project

## Validation commands

- `dotnet build`
…
```

> [!NOTE]
> **New to this?** The validation commands in the map are what CodeLead found in the project files. The map runs nothing. Whether a command passes is for [the gate](validation-and-the-gate.md) to say.

When the project declares its commands in `.codelead/validation.json`, the map lists them first, marked as declared. The gate runs those commands, so the map marks the others as detected:

```output
## Validation commands

- `msbuild sampleapp.slnx /nologo` (declared in `.codelead/validation.json`)
- `dotnet build` (detected; the gate runs the declared commands in its place)
```

### Fresh or stale

The map carries a **stamp**: the git head, whether there were changes not committed, and the number of files. The map is fresh while the git head is the same and the file count moves by 2% or less. When the head moves, or the count moves more, the map is stale. CodeLead then reads the repository again, and the first line says why: `Repository map was stale: the git head moved from … to …`.

### Who writes it

- `codelead init`, except in an empty folder, where there is nothing to read yet.
- `codelead map` and `/map`, when the map is stale, or always with `--refresh`.
- The end of a new app's build, in a folder that `codelead init` set up. The map of the new app is written once, after the build's last line.

### Who reads it

- **The preflight** adds an "App map" section to its prompt, in about 1,500 characters. It lists the modules, the entry points and the files that match the request.
- **The chat** reads the map as one of its sources.
- **The request lint** of [`codelead lint`](../cli/codelead-lint.md) notes a file that the request names and the map does not hold.
- **The context collector** takes the map's relationships when no file changed after the map was written. This saves time on a large repository.

The preflight and the chat write a stale map again before they read it. The lint reads only a fresh map.

## What it is not

- **Not written by a model**. The same code gives the same map. Do not edit it by hand: the next read writes it again.
- **Not the file choice for a request**. The [scan](../cli/codelead-scan.md) and the retrieval still choose the files for each request. The map gives context, not the selection.
- **Not a test result**. It lists commands that were found, not commands that passed.

## Details

- **Files**. `docs/codelead/repository-map.md` and `docs/codelead/repository-map.json` (schema `codelead.repository-map/1`). The map is also registered in `docs/codelead/CATALOG.md` and `catalog.json`.
- **The stamp** in the JSON: `stamp.head`, `stamp.dirty`, `stamp.fileCount`, `stamp.libraryHash` and `stamp.filesHash`.
- **The seed**. A map that is written adds or updates entries in the [encyclopedia](knowledge-base.md): the stack, the validation commands and the modules. It writes one [evidence record](evidence-records.md) with `command: "map"`. A fresh map that is only read adds nothing. Readers of increments, such as [`codelead pr`](../cli/codelead-pr.md), pass over map records.
- **The switch**. `CODELEAD_REPOSITORY_MAP=0` keeps the map out of every reader for a run, and the end of a build then writes no map.
- **Never in the way**. A map that cannot be made never stops `codelead init` or a build. CodeLead prints one line, and the command goes on.

> [!TIP]
> **For experienced users:** commit the map with the code. A reviewer then sees in the pull request how the stack or the modules changed.
